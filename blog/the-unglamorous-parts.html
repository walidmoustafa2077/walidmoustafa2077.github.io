The unglamorous parts

The delegation logic took an afternoon. Making a terminal behave took two weeks.

  • Nov 21, 2026
  • 1 min read
  • Development

The part of building an agent tool I was excited about was the delegation model. A senior agent that reads a ticket and decides whether it's small enough to hand off, a junior agent that does the mechanical work. That took an afternoon.

The other two weeks went into making a terminal behave and keeping configuration files in sync across a repository. Neither of those is interesting to read about. Both were most of the work.

What I thought the work was

When you describe a tool like this to someone, you describe the architecture. Roles, handoffs, the pipeline from intent to tickets. It draws well on a whiteboard, and it's the part that feels like engineering.

It is also the part where mistakes are cheap. If the delegation rule is wrong, you change a condition and run the tests again. The feedback loop is seconds long. You are working in a language you know, with types that tell you when you're wrong.

The terminal

Then you need the agent to actually run commands, and you discover that spawning a process and reading its output are two different problems. Process spawning is solved. Reading a live stream of output from an interactive program is not, on Windows, in the way you want.

A pseudo-terminal is not a pipe. Programs behave differently when they detect one — they buffer, they emit escape codes, they wait for a prompt that a pipe will never send. You get output that arrives in a lump after the process exits, or never, or with colour codes baked into the middle of the string you were trying to parse.

Quoting is its own trap. This is the shape of the problem: 

// You want to run:  node script.js "a b"
// What you write in a shell string is not what the shell receives.
spawn("powershell.exe", ["-Command", `node script.js "${arg}"`]);
//                       ^ two layers of parsing between you and the argv

Each layer eats a different set of characters. Arguments containing spaces, quotes, dollar signs, or a leading dash pass through some layers intact and get mangled by others. The failures are intermittent, which is the worst property a bug can have, because intermittent failures teach you nothing when you retry them.

Nobody posts about the two weeks. It's not interesting to read, and it's most of the work.

Configuration drift

The second time sink was duller still. Agent tools accumulate configuration — which skills exist, which subagents are available, what each one is allowed to do. Some of it lives in project files, some in a home directory, some is generated. Add a feature and you add a file.

The failure mode is silent. Nothing throws when two configs disagree; you just get an agent that behaves inconsistently depending on which directory you launched it from. It took me longer than I'd like to admit to understand that the bug wasn't in the agent, it was in my belief that the files were in sync.

The fix was not clever. One source of truth, generated outward, with a check that fails loudly when the generated copies drift. Boring, and it removed a whole category of confusing behaviour.

What I'd say to someone starting

  • Budget your time for the plumbing, not the architecture.
  • Assume anything involving a shell will take a day longer than you think.
  • When output is intermittent, suspect parsing before you suspect the program.
  • Generated config needs a drift check, or it will silently rot.

I don't regret the two weeks. The tool works because of them, not in spite of them. But if you're building in this space and you're stuck on making a terminal behave while the interesting part waits, you're not doing it wrong. That is the job. The architecture gets the post; the plumbing gets the product shipped.
