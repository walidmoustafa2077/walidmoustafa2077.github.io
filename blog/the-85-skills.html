Eighty-five skills, not five hundred tools

More tools is not more capability. It is more ways to pick wrong.

  • Nov 30, 2026
  • 1 min read
  • Development

A pattern I keep seeing in agent tooling is a tool count used as a selling point. Five hundred tools, a thousand integrations. But a model choosing from five hundred tools is not more capable than one choosing from twenty; it is more likely to pick the wrong one, and harder to predict when it does.

let-me-code goes the other way. It ships about eighty-five skills, each one a short procedure rather than a capability: how to do TDD here, how to apply YAGNI here, how to review a diff here. Skills are habits, not tools.

The rule that makes it stick

Every agent opens by loading the skill that governs its job and reports the list in the skills: line of its handoff. An agent that reports none is re-dispatched instead of trusted. 

skills: systematic-debugging, test-driven-development
status: done
ticket: TICKET-14

That single line is the difference between a policy and a suggestion. If you do not check, agents drift back to improvising within a few turns, and improvising is exactly what you were trying to avoid.

Where they came from

Most of the library is curated from open sets rather than written from scratch: the process backbone from superpowers, the minimalism and YAGNI discipline from ponytail, plus delegation and quality-gate skills from other sets. The provenance and cross-set conflict analysis live in skills-inventory/, which is the part I would read first if I were adopting this.

The cost worth knowing

Scaffolding copies the skills as-is, so a new project receives all eighty-five, about 37 MB in total. Thirty-three of those megabytes are one folder: a photography and scene library used by the design-taste skill. A project with no UI can delete it with no loss.

A capable agent with no habits improvises. Improvising is the problem you were paying to solve.

Full inventory and per-skill notes are in the documentation site.
