Delegation beats one big chatbot

Why planning, implementation, review and commit should be different agents with different permissions.

  • Dec 3, 2026
  • 1 min read
  • Development

Most people start with one agent and one long conversation. It works until the project gets big enough that the same context has to hold the plan, the code, the review notes and the commit message at once. At that point quality does not degrade gracefully. It collapses, and you usually notice a day later.

let-me-code is built on the opposite assumption: a roster of specialised subagents, a library of workflow skills, and a delegation MCP server that orchestrates them. Planning, implementation, review and commit are different agents with different permissions, instead of one chatbot doing all of it.

What the roster looks like

The factory ships an architect, a senior-dev, a qa-engineer, a git-agent and a tech-writer, among others. Each has a narrow job and its own instructions. The orchestrator is the only agent you talk to. 

npx github:walidmoustafa2077/let-me-code

That one command copies the factory assets, merges opencode.json, installs the MCP dependencies, and optionally initialises git. It is additive: it never clobbers a config you already have.

Two gates, by design

The run stops for you twice before any code exists. The spec is shown to you, then the ticket list, and nothing is built, committed or dispatched until you say yes. Silence is not approval.

The most useful thing a senior agent does is refuse to start until the problem is small enough.

This is the part that sounds like ceremony and is not. A single agent that has already written forty lines will rationalise those forty lines. An agent that has to produce a spec and get a yes does not get that option.

Separation of duties is a security property

The reason to split commit from implement is not tidiness. It is that the agent writing code should not be the agent deciding whether the code is good, and neither should have unrestricted shell access. Different permissions per role is a containment strategy, not a workflow preference.
