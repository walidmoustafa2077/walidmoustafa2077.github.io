The upgrade problem nobody thinks about

Installers are easy. Getting fixes into projects that already installed you is the hard part.

  • Nov 21, 2026
  • 1 min read
  • Development

The first version of any scaffolding tool has one behaviour: copy the files in. It works, and it creates a permanent problem. A project that has already been scaffolded keeps the version it was born with, which means every bug fix you ship afterwards reaches nobody who already started.

Make the default additive

A plain run of let-me-code is additive. It keeps every file the project already has. That is the safe default: running the installer twice should never silently destroy someone's work.

Updating is therefore an explicit act, not a side effect: 

node bin/cli.mjs init ../my-project --upgrade --no-install --no-test

What --upgrade actually does

  • Replaces only the factory's own files: agent definitions, skills, the delegation server, the config.
  • Skips every byte-identical file, so a no-op upgrade writes nothing.
  • Keeps a .bak- copy of each file it actually changes.
  • Still merges opencode.json, so project-local settings survive.
  • Never touches your own files: board, intent, tickets, docs, source.

The merge point is the subtle one. A naive upgrade would rewrite the config wholesale and silently drop a pinned DELEGATION_ROOT or a project-specific agent override. Those are exactly the settings a user is least likely to remember they had.

Every file you overwrite without a backup is a support ticket you wrote for yourself.

The general shape

If you ship scaffolding, decide early which files are yours and which are the user's, and write that boundary down. Everything else follows: what an upgrade may replace, what it must merge, and what it must never touch. Deciding it after the fact means every install is already a fork.
